# Стандарт кодирования SQL

Общекорпоративный стандарт оформления кода на SQL для PostgreSQL (второстепенно — SQLite; нагрузка OLTP).

Цель стандарта — снизить когнитивную нагрузку при чтении кода, удешевить типовые правки и уменьшить шум в diff. Правила оформления перестают быть предметом вкусовых споров: у каждого есть идентификатор, уровень обязательности и машинная проверка.

> Статус: **Draft**, версия **0.3.0**. Источник истины — этот репозиторий; публикация — Confluence.

## Быстрый старт

Стандарт живёт целиком в репозитории и проверяется локально. Нужен только Python 3 и SQLFluff.

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

python3 scripts/check.py --all                    # корпус + сверка согласованности
python3 scripts/check.py                          # только корпус, полный профиль
python3 scripts/check.py --config .sqlfluff.base  # только корпус, базовый профиль
python3 scripts/check_consistency.py              # только сверка документа и конфига
```

Ожидаемый результат: `OK: 40 фикстур совпали` и `согласованность документа и конфига подтверждена`.

Ту же команду можно повесить на коммит — включите pre-commit-хук один раз в клоне:

```bash
git config core.hooksPath .githooks
```

## Область и границы

- **В области:** текст на SQL — запросы, функции и представления на `LANGUAGE sql`, DDL-миграции. Форматирование и Нейминг покрыты полностью, Синтаксис — ядром для v1.
- **Вне области:** plpgsql и тела функций/процедур; дизайн БД, производительность и безопасность как аспекты. Подробнее — `docs/adr/0001-scope-aspects.md`, `docs/adr/0002-plpgsql-out-of-scope.md`.
- **Приоритет диалектов:** стандартный SQL → Postgres-first → SQLite не должен ломаться (`docs/adr/0003-dialect-priority.md`).

## Как читать стандарт

- Каждое правило имеет устойчивый ID вида `<аспект>-<номер>`: `FMT-…` (форматирование), `NAM-…` (нейминг), `SYN-…` (синтаксис). В комментариях ревью ссылайтесь на ID — так замечание однозначно.
- Уровни обязательности: `MUST` / `SHOULD` / `MAY` и их связь с RFC 2119 описаны в §4 `STANDARD.md`. `MUST` ↔ `error`, `SHOULD` ↔ `warning` в линтере.
- У каждого правила есть пример «плохо/хорошо» и поле «проверяется линтером».
