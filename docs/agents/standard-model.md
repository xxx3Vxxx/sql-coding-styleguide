# Модель стандарта и инварианты согласованности

Справка для агентов: как устроен `STANDARD.md`, как правило связано с §8.2 и с
конфигами линтера, и что именно проверяет `scripts/check_consistency.py`.
Читать **до** правки правил, §8 или конфигов — чтобы конфликт уровней или
маппинга не всплыл уже на реализации.

## Правило

- Заголовок `### <ID> — <название>`; ID вида `FMT|NAM|SYN`-NNN.
- Тело: `**Уровень нормативности:**` (MUST/SHOULD/MAY), `**Правило.**`,
  `**Плохо:**`, `**Хорошо:**`, `**Обоснование.**`, `**Проверяется линтером:**`
  (да/нет).
- **ID стабильны**: не перенумеровываются, «дырки» в нумерации допустимы и
  намеренны. Новое правило получает следующий свободный номер.
- **Одно правило — один уровень нормативности.** Нельзя «поднять» одно
  предписание до MUST, оставив другое в том же правиле на SHOULD: это либо два
  правила, либо явное решение по уровню всего правила. Типовой источник
  конфликтов при доработке.
- Все ```sql-блоки в секции `**Хорошо:**` обязаны быть линтер-чистыми
  (`run_doc_blocks` в `scripts/check.py`).

## §8.2 — таблица маппинга

Строка вида `| ID | Уровень | Проверяется линтером | SQLFluff |`:

- покрывает **ровно** все правила документа — без пропусков и без лишних строк;
- уровень и признак «да/нет» совпадают с телом правила;
- ячейка SQLFluff перечисляет имена правил линтера (напр.
  `LT14 layout.keyword_newline`).

## Связь с конфигом линтера

- **«Проверяется линтером: да»** → имя правила включено в `rules` полного
  профиля; обязательна пара фикстур `examples/<id>-good.sql` +
  `examples/<id>-bad.sql` (ожидаемые коды — в заголовке `-- expected:`).
- **«нет»** → фикстур быть не должно; правило живёт только как текст (проверка
  на ревью).
- Каждая секция `[sqlfluff:rules:<name>]` сопровождается комментарием со ссылкой
  на ID стандарта.

## Профили

- `.sqlfluff` (полный, «aspirational»): MUST → `error`, SHOULD-проверяемое →
  `warning` (ключ `warnings`).
- `.sqlfluff.base` (базовый, «errors only»): MUST → `error`,
  SHOULD-проверяемое перечислено в `exclude_rules`.
- Список `rules` в профилях совпадает; **все прочие секции и значения, включая
  layout-секции, идентичны** (забытая в одном файле секция — ошибка).

## Где проверяется

```bash
python3 scripts/check.py --all   # корпус + блоки «Хорошо» + согласованность
python3 scripts/check.py         # корпус + блоки «Хорошо»
python3 scripts/check_consistency.py
```

CI (`.github/workflows/check.yml`) гоняет `check.py --all` на push в `master` и
на PR. Правило, не покрытое ни фикстурой, ни проверкой §8, гейт не пройдёт.

## Классы изменений (§9.1)

Удаление правила и запрет ранее валидного кода — класс MAJOR. При черновике
(`0.x`) это минорная версия плюс пометка в ADR и в §9.3.
