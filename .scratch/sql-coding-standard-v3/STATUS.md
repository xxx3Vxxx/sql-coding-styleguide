## Что решено (грилинг владельца, 2026-11-01)

| # | Решение |
|---|---|
| 1 | Батч узкий: правила не на все DML-конструкции, а только там, где линтер слеп |
| 2 | Все три формы списков **допустимы**: (a) брекетный вид, (b) одиночная строка на строке с ключевым словом, (c) многострочный список без брекетов |
| 3 | Канон (`SHOULD`) — (a), кроме списка из одного элемента: он остаётся на строке с ключевым словом (аналогия с `FMT-008`) |
| 4 | Перенос `values`/`set` закрывается **конфигом** (`LT14`) → эффект `MUST` → `0.3.0`/`MAJOR` |
| 5 | `values`/`set` входят в термин «Корневое ключевое слово»; `returning` — **нет** (нет узла-клаузулы в парсере), его расположение регламентирует `FMT-016` текстом |
| 6 | `FMT-016` — новое `SHOULD`, «проверяется линтером: нет»; включает формы списков, `returning`, вложенность upsert |
| 7 | `MERGE`, `DELETE ... USING`, DDL — вне этого батча |

## Опорные факты (проверено на SQLFluff 4.5.0, postgres)

- `values`/`set`: `[sqlfluff:layout:type:values_clause|set_clause_list]`
  `keyword_line_position = leading` → `LT14` «keyword should always start a new
  line». Однострочный `insert ... values (...)` после этого невалиден.
- `returning`: узла-клаузулы нет; секция `returning_clause` принимается, но
  инертна → только текст.
- Формы списков конфигом не выражаются: `[sqlfluff:layout:type:bracketed]
  line_position = alone` инертен (проверено).
- `LT02` навязывает отступы внутри upsert: `do update` → `set` +4, элементы +8.
- «Выравнивание в столбец» (padding) уже запрещено `LT01`/`FMT-007` — к вопросу
  об отступе отношения не имеет.
