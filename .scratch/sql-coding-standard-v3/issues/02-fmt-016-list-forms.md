# 02: Новое SHOULD-правило FMT-016 — канон форм списков и `returning`

**What to build:** в документе появляется явный канон записи DML-списков: одиночный
элемент остаётся на строке с ключевым словом, несколько элементов идут брекетным
видом. При этом все три формы (брекетный список, короткая запись, многострочный
список без брекетов) остаются допустимыми, а читатель понимает, какая из них
предпочтительна и почему линтером это не проверяется. Там же регламентировано
расположение `returning` и вложенность upsert.

**Blocked by:** 01 (термин «Корневое ключевое слово» расширяется в 01, канон
ссылается на него и на `FMT-008`/`FMT-015`; правки в один и тот же §8.2 идут
последовательно)

**Status:** ready-for-agent

- [ ] `FMT-016` (`SHOULD`, «Проверяется линтером: нет») добавлено в §5 после
      `FMT-015`, номер не занят (016 — следующий свободный).
- [ ] Правило фиксирует канон: список из одного элемента — на строке с ключевым
      словом; список из нескольких элементов — `(` на отдельной строке, элементы
      с отступом 4, `)` по левому краю; многострочный список без брекетов
      (элементы по левому краю) — допустимое отступление.
- [ ] Правило фиксирует расположение `returning` (один элемент — на строке с
      ключевым словом, несколько — по одному на строку с отступом 4) и
      вложенность upsert (`do update`: `set`/`where` на уровень внутрь).
- [ ] Обоснование объясняет, почему канон не навязывается линтером (`returning`
      без узла-клаузулы, для форм списков конфиг-рычага нет) и ссылается на
      `ADR-0007` как на причину допустимости трёх форм.
- [ ] Блоки «Плохо»/«Хорошо» показывают все три формы; каждый ```sql в
      «Хорошо» линтер-чист.
- [ ] В §8.2 добавлена строка `| FMT-016 | SHOULD | нет | — |`; фикстур у правила
      нет (инвариант «нет» → без `examples/`).
- [ ] `python3 scripts/check.py --all` зелёный; в документе 36 правил.
