# 02: Новое SHOULD-правило FMT-016 — канон форм списков и `returning`

**What to build:** в документе появляется явный канон записи DML-списков: одиночный
элемент остаётся на строке с ключевым словом, несколько элементов идут брекетным
видом. При этом все три формы (брекетный список, короткая запись, многострочный
список без брекетов) остаются допустимыми, а читатель понимает, какая из них
предпочтительна и почему линтером это не проверяется. Там же регламентировано
расположение `returning` и вложенность upsert.

**Blocked by:** 01 (термин «Корневое ключевое слово» расширяется в 01, канон
ссылается на него и на `FMT-008`/`FMT-015`; правки в один и тот же §8.2 идут
последовательно)

**Status:** done

- [x] `FMT-016` (`SHOULD`, «Проверяется линтером: нет») добавлено в §5 после
      `FMT-015`, номер не занят (016 — следующий свободный).
- [x] Правило фиксирует канон: список из одного элемента — на строке с ключевым
      словом; список из нескольких элементов — `(` на отдельной строке, элементы

- [x] `python3 scripts/check.py --all` зелёный; в документе 36 правил.

## Decisions

- Канон брекетного вида сформулирован для списка `values` (кортежи-строки); для
  списка `set` брекеты явно не применяются — присваивания идут по одному на
  строку с отступом 4 (брекетная запись `set` LT02-грязна и в «Хорошо» не
  ставится).
- Три формы закреплены явно: одиночный элемент на строке с ключевым словом,
  брекетный вид для нескольких, многострочный список без брекетов как допустимое
  отступление (ровно его выдаёт `sqlfluff fix`); в «Плохо» показана только
  неканоничная краткая форма с несколькими кортежами на строке `values`.
- Ссылка на `ADR-0007` сделана в прозе без inline-кода (путь
  docs/adr/0007-dml-layout.md), потому что файл создаёт тикет 03, а
  `check_consistency.py` считает inline-пути из `docs/` битой ссылкой.
- Фикстур не добавлено: правило `нет` держит инвариант
  `check_consistency.py` («нет» → без `examples/`), а чистоту канона проверяют
  семь новых ```sql-блоков «Хорошо».
